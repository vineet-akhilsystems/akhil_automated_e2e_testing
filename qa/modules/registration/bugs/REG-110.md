# Bug Report: REG-110 — "Update" Button Is Enabled Immediately Upon Opening an Existing Patient Record Before Any Edits

- **Case ID:** `REG-110`
- **Module:** Patient Registration — Edit Existing Registration (`RegistrationPreview.jsx`)
- **Severity:** Medium (Broken Dirty-State Tracking / Accidental Unchanged Updates)
- **Priority:** P2
- **Environment:** `https://demo.augastam.com/registration/1101f999-7c91-4ba5-a52b-a80d728c588e/ASNR0000000445` (Build `2.0.66`)
- **Status:** Confirmed Product Bug

---

## 1. Summary
When opening an existing patient registration via `/registration/<workflowId>/<UHID>` (or by selecting a patient from the top-bar search), the **Update** button is meant to remain disabled until the user modifies at least one field (`disabled={saving || loading || (isExistingRegistration && !isFormDirty)}` with tooltip `"No changes to update"`). However, due to a race condition between capturing `originalCombinedPropertiesRef.current` and asynchronous Redux/child-component state initialization, `isFormDirty` immediately flips to `true` on load, enabling the **Update** button before any user interaction.

---

## 2. Steps to Reproduce
1. Navigate to an existing registration record, e.g. `/registration/1101f999-7c91-4ba5-a52b-a80d728c588e/ASNR0000000445` (or pick a patient from the top-bar search).
2. Wait for the form fields to populate. Do not click or type into any field.
3. Inspect the **Update** button in the top-right action bar.

---

## 3. Expected vs. Actual Result
- **Expected:**
  - The **Update** button is disabled (`disabled = true`) with tooltip `"No changes to update"` until a field is modified.
- **Actual:**
  - The **Update** button is enabled (`disabled = false`) immediately after the form finishes loading, allowing unnecessary `PUT /patient-registration/update-details` calls with no user edits.

---

## 4. Root Cause Analysis (Hypothesis with Code Reference)
- **File:** `custom-form-builder/src/pages/registration/RegistrationPreview.jsx:1873-1942` & `2850-2872`
- **Code Logic:**
  ```javascript
  // RegistrationPreview.jsx:1873-1929
  applyPatientDetailsToForm(patientDetails); // Dispatches Redux updateRegistrationFormValues asynchronously
  ...
  // Immediately snapshots baseline BEFORE Redux state & child webpart effects settle:
  originalCombinedPropertiesRef.current = buildCombinedProperties({
    formValues: formValuesRef.current,
    tableData: tableDataRef.current,
    ...
  });
  setIsFormDirty(false);
  ```
  And in the dirty-check effect (`RegistrationPreview.jsx:2850-2872`):
  ```javascript
  useEffect(() => {
    if (!isExistingRegistration) return;
    if (!originalCombinedPropertiesRef.current) return;
    const currentCombined = buildCombinedProperties();
    const isSame = areCombinedPropertiesEqual(currentCombined, originalCombinedPropertiesRef.current);
    setIsFormDirty(!isSame);
  }, [isExistingRegistration, formValues, tableData, selectedTypeId, ...]);
  ```
- **Why It Fails:**
  1. `applyPatientDetailsToForm(patientDetails)` updates `formValuesRef.current` and dispatches `updateRegistrationFormValues(mergedValues)`, then `originalCombinedPropertiesRef.current` is captured synchronously on line 1924.
  2. Immediately afterward, child components (`DateField` age calculation, `PinCodeField` initial address hydration, `Payer` default selection, or multilevel lookup normalization) dispatch follow-up field updates on mount/render.
  3. Those post-load normalization updates change `formValues` / `tableData`, causing `areCombinedPropertiesEqual(currentCombined, originalCombinedPropertiesRef.current)` to return `false` and setting `isFormDirty = true` before the user touches anything.

---

## 5. Recommended Fix
Re-snapshot `originalCombinedPropertiesRef.current` after initial form/child hydration stabilizes (or track dirty state only after an explicit user interaction event / `userModified` flag rather than background mount effects).
